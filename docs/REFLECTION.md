# 反思题回答

> 对应需求文档「十四、反思题（0 分，不计分）」

---

## 1. 为什么 V2 下单导入链路不能继续采用同步阻塞方式？什么时候同步反而更简单可靠？

**为什么不能继续同步**：

V2 的同步阻塞模式在一次 HTTP 请求中完成文件解析 → 规则引擎 → 逐行校验 → 逐行 INSERT 的全流程。在 10,000 行文件场景下，即使每行仅 200ms，总耗时也超 30 分钟，远超 Vercel Serverless 的请求超时上限（函数 55s、边缘 30s）。同时数据库连接在请求生命周期内被持续占用，多用户并发时连接池迅速耗尽，导致雪崩。

**什么时候同步更简单可靠**：

- 小文件场景（< 100 行），全链路耗时 < 5 秒，用户等待可接受；
- 内部管理后台的即时操作，如手动录入单条运单；
- 不需要可观测性和错误追溯的简单场景。

同步模式的优势在于：代码简单（无队列/Worker/Outbox）、故障模型直观（报错即返回）、无需维护额外基础设施。异步架构引入后，消息丢失、重复消费、幂等设计、任务卡死恢复等复杂度显著上升。当吞吐要求不高且文件规模可控时，同步是更务实的选择。

## 2. 处理单元变大或变小，会分别带来什么影响？

| 维度 | 处理单元变大（如 2000 行/批） | 处理单元变小（如 500 行/批） |
|---|---|---|
| 批次总数 | 更少，Outbox 事件少，调度开销低 | 更多，调度和状态更新开销增大 |
| 单批耗时 | 更长，可能逼近 Vercel 55s 上限 | 更短，不易超时 |
| 重试成本 | 单批失败重试成本高（2000 行全部重跑） | 重试成本低（仅 500 行） |
| 数据库事务 | 大事务锁表风险更高 | 小事务更安全 |
| 幂等粒度 | 粗粒度，进度精度低 | 细粒度，进度更新更频繁 |
| 并发度 | 低，多 Worker 并行度受限 | 高，更多批次可并行消费 |

本项目选择 **1000 行/批** 作为平衡点：单批耗时约 3-5 秒（解析 + 规则 + 校验 + 插入），在 Vercel 55s 上限下每次 dispatch 可处理约 4-6 批。若需优化 60 秒全链路目标，可改为 500 行/批提高并发度。

## 3. 如果吞吐目标从 10,000 单/分钟提升到 50,000 单/分钟，最先成为瓶颈的是 Worker、队列还是数据库写入？你会如何扩展？

**最先瓶颈：数据库写入**。

原因：
- 实测数据：单批 1000 行 insert 阶段耗时 2157ms（P50），占单批总耗时 65%+；
- 50,000 行 = 50 批次，全量 insert 耗时约 50 × 2.2s = 110s（串行），即使并发 4 Worker，仍需 ~28s 纯 DB 写入时间；
- Neon Serverless 连接池有限（pooler 模式下默认约 20 连接），高并发写入会排队。

**扩展方案**：
1. **写入优化**：将单条 VALUES 改为 `COPY` 协议或 `UNNEST` 批量写入（已在 `db-v4-writer.ts` 实现），减少 SQL 解析开销；
2. **连接池扩容**：升级 Neon 实例到更高规格，增加连接数；
3. **分片写入**：按批次哈希到不同 DB 实例（写分离）；
4. **Worker 扩容**：部署常驻 Worker（Railway/Fly.io），突破 Vercel 55s 单函数限制，实现 8-16 并发消费；
5. **队列升级**：将 Outbox+Dispatcher 自研模式改为 BullMQ + Redis，支持更强的背压和并发控制。

## 4. 如果队列消息重复投递，为什么"业务幂等"比"消息只投递一次"更重要？

**消息只投递一次（exactly-once）是理想目标，但分布式系统中无法绝对保证**。

原因：
- 网络分区、Broker 宕机、Consumer 崩溃都可能导致"已处理但 ACK 丢失"，Broker 重投；
- 实现 exactly-once 需要 Broker 和 Consumer 协作，引入分布式事务，复杂度极高且性能下降显著；
- 大多数队列系统（BullMQ、Redis Streams、AWS SQS）仅保证 at-least-once。

**业务幂等是务实之选**：
- `ON CONFLICT DO NOTHING` 基于稳定业务键（如 external_code + sku_code）去重，重复写入不产生脏数据；
- `recomputeTaskProgress` 每次全量重算进度，不依赖增量累加，天然幂等；
- `upsertBatchResult` 按 batch_index 精确 UPDATE 批次结果，重试不重复累计。

结论：在分布式系统中，"接受 at-least-once + 业务层保证幂等"比"追求 exactly-once"成本更低、可靠性更高。

## 5. 如果某个处理单元中有部分行失败，你认为应该整体回滚还是成功行先入库？为什么？

**成功行先入库（partial success 模式）**，原因：

1. **大促场景的可用性优先**：10,000 行中即使 1% 失败，也应有 9,900 行成功入库。整体回滚意味着用户损失 100% 的工作，不可接受；
2. **失败隔离**：每行独立校验（SKU、格式、必填），行间无依赖，失败行不影响成功行；
3. **可修复性**：失败行写入 `import_task_errors`，用户可定位具体问题后修正重传，而不是从头开始；
4. **本项目的实现**：成功行通过 `writeBatch` 批量 UPSERT 入库，失败行写入 `import_task_errors`，任务状态为 `PARTIAL_SUCCESS`。

整体回滚仅在以下场景合理：事务性强、行间有业务依赖（如总金额=各行金额之和），但本项目的运单导入属于独立行操作，无此约束。

## 6. 错误明细中需要保留原始值，但手机号和地址属于敏感信息，你如何平衡排障效率和数据安全？

本项目采用 **字段级脱敏** 策略（`maskValue` 函数）：

| 字段类型 | 脱敏规则 | 示例 |
|---|---|---|
| 手机号 | 保留前 3 后 4 位，中间用 `****` 替代 | `138****1234` |
| 地址 | 保留省市，详细地址用 `***` 替代 | `湖南省长沙市***` |
| 身份证 | 保留前 6 后 4 位 | `430102****1234` |
| 普通字段 | 不脱敏 | SKU_00123 |

**平衡策略**：
- 脱敏在 **写入 `import_task_errors` 前** 执行，确保落库数据不含明文敏感信息；
- 脱敏后仍保留足够信息用于排障（如手机号前缀可判断运营商、地址省市可判断区域错误）；
- 如需完整原始值排查，运维可从原始上传文件中定位对应行（通过 `row_number` 字段）；
- 数据库层面：`import_task_errors` 表不建全文索引于 `raw_value` 列，减少泄露面。

## 7. 如果 Outbox 表持续增长到千万级，你会如何清理、归档和设计索引？

**索引设计**：
- `(status, next_retry_at)` 复合索引 → Dispatcher 轮询 `WHERE status='PENDING' AND next_retry_at <= NOW()` 高效命中；
- `(aggregate_id)` 索引 → 按任务查询关联事件；
- `(created_at)` 索引 → 清理策略依赖。

**清理策略**：
1. **已完成事件定期清理**：`status IN ('SENT','FAILED') AND sent_at < NOW() - INTERVAL '7 days'` 的事件每日定时删除（Vercel Cron 或外部调度）；
2. **死信归档**：`retry_count >= 5 AND status = 'FAILED'` 的事件归档到 `event_outbox_archive` 表（或导出到 S3/日志系统），保留 30 天后删除；
3. **分区表**（PostgreSQL 12+）：按 `created_at` 月分区，清理时直接 `DROP PARTITION`，避免大表 DELETE 锁；
4. **监控告警**：outbox 总量超过 100 万条时触发告警，提醒人工检查是否有积压异常。

**归档方案**：
- 冷数据（30 天以上）导出为 CSV/JSON 存入对象存储；
- `event_outbox_archive` 表只保留近 90 天数据供审计。

## 8. 如果 AI 生成的解析规则导致大量字段映射错误，监控系统如何帮助快速发现是规则问题而不是数据库问题？

**监控看板的分层定位能力**：

1. **阶段耗时异常 → 指向规则问题**：
   - 如果 `rule_duration_ms` 正常（几十 ms）但 `validate_duration_ms` 暴增，说明规则执行成功但校验大量失败 → 规则映射可能正确但数据质量问题；
   - 如果 `parse_duration_ms` 正常但 `rule_duration_ms` 异常（如从 30ms 飙到 3000ms），说明规则引擎执行异常 → 可能规则配置错误导致死循环或复杂聚合。

2. **错误分布突变 → 指向规则问题**：
   - 如果某规则下 `E006（规则映射失败）` 占比突然从 1% 飙升到 50%，大概率是 AI 生成的规则字段映射错误；
   - 对比不同规则下同一文件类型的错误率：新规则错误率远高于已有规则 → 规则问题。

3. **Trace 搜索 → 精确诊断**：
   - 按 `trace_id` 查询时间线，找到 `ImportBatchStarted` → `ImportBatchFailed` 的时间差；
   - 点击失败节点查看具体错误码和字段：`E006: 规则映射失败, field=skuCode` → 确认为规则字段映射错误，而非数据库写入失败（`E007`）。

4. **区分规则问题 vs 数据库问题**：
   | 信号 | 规则问题 | 数据库问题 |
   |---|---|---|
   | 错误码分布 | E006 占比高 | E007 占比高 |
   | 阶段耗时 | rule_duration_ms 异常 | insert_duration_ms 异常 |
   | 失败时机 | 校验/映射阶段 | 写入阶段 |
   | 影响范围 | 特定规则下全部文件 | 所有文件 |
   | 数据库连接 | 正常 | 连接池耗尽/超时 |

5. **快速修复流程**：
   - 运维在监控看板发现错误率飙升 → 点击 `error_distribution` 跳转错误明细 → 筛选 `E006` → 看到大量 `field=skuCode` 映射失败 → 确认是 AI 生成的解析规则中 SKU 字段映射到了错误的列 → 通知用户修正规则或切换到备用规则。
